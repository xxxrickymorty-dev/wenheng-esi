## 0. 我第一版判断错了，改在这里

第一版结论是数出来的（92 个路由中位数 20.5 行 / App.tsx 19 处 useState），说「后端分层是对的，前端状态失控」。

抽样读码之后，两条都站不住：

| 第一版判断 | 实际读到的证据 | 判定 |
|---|---|---|
| 后端只是「堆在一个文件」 | `api_forecast_choice`（行 1481）里同时做：参数校验、JSON 类型检查、调 `forecast_choice.validate`、写文件；`_forecast_choice_period_is_safe` 这类辅助函数也塞在 app.py | ❌ 不是纯薄壳，**路由层混了校验与业务** |
| 前端 19 个 useState = 失控 | `refreshDetail`（行 114）用 `detailRequestByPeriodRef` 计数器做**竞态保护**，按 `period` 做 key 缓存 | ❌ 写法是对的，属于**手写但正确**；问题是同一套模式复制了 4–5 遍 |
| 新增（第一版没看见） | `forecast-choice` 有两条路由（GET / GET+POST），注释原文：「此前被误挂成 post…FastAPI 按注册顺序匹配，POST 会被这条抢先接走」 | ✅ **真缺陷**：路由表依赖注册顺序，是隐式契约 |

**所以真实问题不是「乱」，是两件更细的事：**

- 后端：路由层职责混杂 + 注册顺序有隐式依赖。
- 前端：并发与缓存模式没有抽象出来，每加一个资源就要复制一遍 ref 计数器。

这两件都**不是重写级的工作**。改法比「重构」轻得多。

> 教训写在 §1.5：数出来的指标只能告诉你「先看哪里」，不能告诉你「该改什么」。

## 1. 强模型的价值在哪（别用错）

| 用法 | 普通模型 | goat 级 | 该给谁 |
|---|---|---|---|
| 写一个 1000 行的页面组件 | 能写，结构烂 | 写得更好，**还是 1000 行** | ❌ 产量活 |
| 判断「这个页面该不该有 19 个状态」 | 不会问 | 给得出 3 种拆分方案 | ✅ 判断活 |
| 定「什么叫做好了」 | 写不出 | 能写出可验证判据 | ✅ 判断活 |
| 一次改 50 个文件 | 会漏 | 也会漏，只是漏得漂亮 | ❌ |

给强模型的输入是**问题 + 约束 + 判据**，不是任务 + 文件清单。

提示词里必须加一句：**「如果你认为我给的目标本身有错，先说，不要照做。」**
不加这句，它会把「重写前端」当圣旨执行，产出更漂亮的一堆巨型组件。

## 1.5 判断分三级——「你的判断不一定对」是对的

| 级别 | 来源 | 能支撑什么决定 | 误判代价 |
|---|---|---|---|
| **L1 指标推测** | 数行数、数 useState、看体积 | 只能决定「先看哪里」 | 高。会指错方向——本文件 §0 就是活例子 |
| **L2 读码判断** | 抽样读关键文件 | 能排优先级 | 中。看不到改动阻力 |
| **L3 探针验证** | 真改一小块，量阻力 | 才能定刀法 | 低。改不动就 revert |

只读的方案最多到 L2。L2 的死穴：**它看得见代码长什么样，看不见改它要连带动多少东西。**

所以答案是：**不要让强模型只列计划，也不要让它直接重构，让它做一根探针。**

探针 = 一个真实的最小改动（一个函数 / 一个文件）。改完量三件事：动了几个文件、测试红几条、撞到什么耦合。这个数据比任何方案都可信。

**用法上有个反直觉的点：让它证伪你，不是验证你。**
提示词写「找出证据证明我这个判断是错的」，不要写「分析这个判断对不对」。
前者会去翻反例，后者只会给你找支撑。

## 2. 四个阶段（P1 是探针，不是方案）

| 阶段 | 它做什么 | 产物 | 你的动作 | 不许做 |
|---|---|---|---|---|
| **P0 体检** | 只读。抽样读关键文件，找问题 | 《问题清单》：每条带文件:行号 + 一句影响 | 圈同意项 | 改任何文件 |
| **P1 探针** | **真改最小一块** | 《探针报告》：动几个文件 / 测试红几条 / 花了多久 / 撞到什么 | 看数据，不看结论 | 扩大范围 |
| **P2 定策** | 按探针结果定刀 | 《升级方案》：分几刀 + 每刀失败怎么退 | 审「演示还能不能跑」 | 改任何文件 |
| **P3 分刀** | 一刀一提交，每刀跑验收 | 代码 + 四条命令全绿 | 亲自跑，不听它说 | 顺手优化 |

**卡点两个，必须卡死：**
1. P2 方案里每刀要写清「失败怎么退」。
2. P3 每刀动手前，它必须先列出「会碰到哪些测试」。

## 3. 赛前 / 赛后两套方案

决赛 2026-11-11（现场）。今天 10-25，剩 17 天。

**方案 A（赛前 17 天）：只修演示路径，不动架构**

| 做什么 | 为什么 |
|---|---|
| 拿 P0 体检报告，只挑「演示时会撞上」的问题 | 评委只看 10 分钟，架构债他看不见 |
| 每条修复限 1 个 commit、限 3 个文件 | 17 天内任何大改都可能毁掉演示 |
| 不碰 `App.tsx` 的缓存与竞态逻辑 | 那套逻辑目前是**对的**；动它只会引入新 bug |

**方案 B（赛后 11-12 起）：真升级，按 §2 四阶段走**

第一刀选前端的「并发 / 缓存模式抽象」，不选后端搬家：

- 前端已经手写了正确的竞态保护与按 key 缓存（`refreshDetail`、`requestForecastChoice`），但**复制了 4–5 遍**。抽成一个 hook，风险低、收益是每加一个资源少写 30 行。
- 后端拆文件不改行为，对评委零价值，属于「等有空」的活；真要动，先把路由层里的校验抽出去（`_forecast_choice_period_is_safe` 那类），顺带消掉「注册顺序」这个隐式契约。
- `docs/重构规划与验收台账` 记着「期次串线」（`Report.tsx`/`Tools.tsx` 用全局最后任务）——**这条我没验证过**，先当线索，别当结论。

## 4. 四段提示词（复制即用）

### P0 体检

```
你在做系统体检，不是重构。只读，不许改任何文件。

先读 REFACTOR.md（135 行）和 web/UX.md 的「四、体验判据」「十、信息减负」两节。

【先证伪】我现在的判断是：前端的问题是「并发与缓存模式复制了 4-5 遍没抽象」，
后端的问题是「路由层混了校验与业务，且路由表依赖注册顺序」。
你的第一个任务不是确认它，是找出证据推翻它。找到反例就直说，别替我圆。

【再体检】范围限定 web/src 与 server/app.py，不看算法。每条给：
- 问题：一句话
- 证据：文件:行号
- 影响：会导致什么具体 bug，或什么具体维护困难
- 代价：修它要动几个文件、要不要改接口

按「演示可见 / 维护困难 / 纯洁癖」三级分类。不要给方案，只做诊断。
```

### P1 探针（这一阶段必须真改代码）

```
选一处「最可能是问题、但光看代码看不准」的地方，做一根探针。

探针规则：
- 只改一处，最多 2 个文件，一条命令能 revert
- 不改接口路径与返回结构
- 改完必须跑 uv run python -m pytest -m ""；改了前端再跑 npm run build

做完给我这张表，不要给结论：

| 项 | 实测 |
|---|---|
| 动了几个文件 | |
| 连带走多少行 | |
| 测试红了几条，分别是哪些 | |
| 花了多久 | |
| 撞到什么事先没料到的耦合 | |

最后一句回答：这次改动推翻了你的哪个预判？
```

### P2 定策

```
基于探针报告，给升级方案。

1. 分几刀，每刀 <=3 个文件、可单独 commit、可单独 revert
2. 每刀写清：改什么 / 不改什么 / 怎么验证没改坏 / 失败怎么退
3. 标出哪一刀风险最高，为什么
4. 明确写出：哪几处「看起来该改，但探针显示不值得改」

约束：接口路径与返回结构不动。演示路径（登录 -> 工作台 -> 生成台 -> 核验定稿）每刀之后都要能用。
不要写代码。
```

### P3 实施（每刀一次）

```
执行第 N 刀。

只准改：<从 P2 方案里抄>
只读：<精确文件:行号区间>
不动：接口路径 / 返回结构 / 演示路径 / 测试文件

动手前先答两个问题，等我确认：
1. 这一刀会碰到哪些测试？
2. 演示路径坏了怎么退？

确认后执行。完成后给我：改了哪几行、跑了什么验证、结果原文。
```
