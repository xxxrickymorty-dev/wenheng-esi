## 0. 先纠正一个前提

你说「架构、前端设计、后端逻辑都没做好」。实测下来只有一处成立：

| 层 | 实测 | 判断 |
|---|---|---|
| 后端 `server/` | 92 个路由块，**中位数 20.5 行**，均值 32 行，只有 4 个超过 100 行 | **分层是对的**。路由是薄壳，业务在 `src/`（26 539 行）。问题只是物理上堆在一个 3021 行的文件里 |
| 前端 `web/src/` | `App.tsx` 817 行、**1 个组件、19 处 useState、12 处 useEffect**；`DialogPage.tsx` 1004 行 / 13 + 8 | **这里才是真问题**：状态编排失控。不是「不好看」 |
| 引擎 `src/` | 26 539 行，最大 `charts.py` 1254 | 本轮不动 |

**结论：后端是「搬家」，前端是「重做状态」。两者成本差一个数量级，不要放进同一个任务。**

## 1. 强模型的价值在哪（别用错）

| 用法 | 普通模型 | goat 级 | 该给谁 |
|---|---|---|---|
| 写一个 1000 行的页面组件 | 能写，结构烂 | 写得更好，**还是 1000 行** | ❌ 产量活 |
| 判断「这个页面该不该有 19 个状态」 | 不会问 | 给得出 3 种拆分方案 | ✅ 判断活 |
| 定「什么叫做好了」 | 写不出 | 能写出可验证判据 | ✅ 判断活 |
| 一次改 50 个文件 | 会漏 | 也会漏，只是漏得漂亮 | ❌ |

给强模型的输入是**问题 + 约束 + 判据**，不是任务 + 文件清单。

提示词里必须加一句：**「如果你认为我给的目标本身有错，先说，不要照做。」**
不加这句，它会把「重写前端」当圣旨执行，产出更漂亮的一堆巨型组件。

## 2. 四阶段（每阶段产物是文档，不是代码）

| 阶段 | 它做什么 | 产物 | 你的动作 | 不许做 |
|---|---|---|---|---|
| **P0 体检** | 只读。找问题、定级、给证据 | 《体检报告》：问题 → 证据（文件:行号）→ 修复代价 | 圈出同意项，删掉不同意的 | 改任何文件 |
| **P1 定靶** | 只读。给目标架构 + 分刀方案 | 《升级方案》：目标结构图 + 分几刀 + 每刀验收判据 | 审「这一刀切下去，演示还能不能跑」 | 改任何文件 |
| **P2 分刀** | 一次一刀，改码 | 一刀 = 一个 commit + 能 revert | 每刀完跑验收 | 顺手优化范围外 |
| **P3 验收** | 回主仓库跑 | 四条命令全绿 | 亲自跑，不听它说 | 只看它的总结 |

**卡点只有两个，但必须卡死：**
1. P1 结束时，方案里每刀必须写清「失败怎么退」。
2. P2 每刀开始前，它必须先列出「会碰到的测试」。

## 3. 赛前 / 赛后两套方案

决赛 2026-11-11（现场）。今天 10-25，剩 17 天。

**方案 A（赛前 17 天）：只修演示路径，不动架构**

| 做什么 | 为什么 |
|---|---|
| 拿 P0 体检报告，只挑「演示时会撞上」的问题 | 评委只看 10 分钟，架构债他看不见 |
| 每条修复限 1 个 commit、限 3 个文件 | 17 天内任何大改都可能毁掉演示 |
| 不碰 `App.tsx` 的 19 个状态 | 改状态 = 改全部交互，风险不可控 |

**方案 B（赛后 11-12 起）：真升级，按 §2 四阶段走**

第一刀选前端状态重构，不选后端搬家：

- 前端 19 个 useState 已经在制造真 bug（`docs/重构规划与验收台账`：`Report.tsx`/`Tools.tsx` 用全局最后任务 → **期次串线**）。
- 后端拆文件不改行为，对评委零价值，属于「等有空」的活。
- 顺序：前端状态 → 后端路由分文件 → `src/` 按需。

## 4. 三段提示词（复制即用）

### P0 体检

```
你在做系统体检，不是重构。只读，不许改任何文件。

先读 REFACTOR.md（134 行）和 web/UX.md 的「四、体验判据」「十、信息减负」两节。

体检目标：找出「限制这个系统继续演进」的结构问题。范围限定 web/src（前端状态架构）与 server/app.py（后端物理结构）。不看算法。

每条问题按这个格式给：
- 问题：一句话
- 证据：文件:行号 + 实际数字（例如 App.tsx 有 19 处 useState）
- 影响：会导致什么具体 bug 或什么具体维护困难
- 代价：修它要动几个文件、要不要改接口

按「演示可见 / 维护困难 / 纯洁癖」三级分类。最后给一句总判断：现在最该动的是哪一处，为什么。

如果你认为我「前端架构没做好」这个判断本身有错，直接说。
不要给建议方案，只做诊断。
```

### P1 定靶

```
基于体检报告里我圈出的 N 条（我下面贴），给一份升级方案。

要求：
1. 目标结构画成文字图（模块 → 职责 → 依赖方向）
2. 拆成若干刀，每刀满足：只动 ≤3 个文件、能单独 commit、能单独 revert
3. 每刀写清：改什么 / 不改什么 / 怎么验证没改坏 / 失败怎么退
4. 标出哪一刀风险最高，为什么

约束：接口路径与返回结构一律不动。演示路径（登录 → 工作台 → 生成台 → 核验定稿）在每一刀之后都必须能用。

不要写代码。不要动文件。
```

### P2 实施（每刀一次）

```
执行第 N 刀。

只准改：<从 P1 方案里抄过来>
只读：<精确文件:行号区间>
不动：接口路径 / 返回结构 / 演示路径 / 测试文件

动手前先回答两个问题，等我确认：
1. 这一刀会碰到哪些测试？
2. 如果改完演示路径坏了，怎么退回来？

确认后执行。完成后给我：改了哪几行、跑了什么验证、结果原文。
```
