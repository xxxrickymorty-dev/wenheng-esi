## 决定

1. **范围**：已收 `approval`、`review`、**`job`**、**`manual_inputs`**、**`sources`**（数据来源清单）。`run_log.json` /
   `audit_record.json` / `env_snapshot.json` **缓做**——它们挂在 `out/<期次>/` 的确定性产物与
   logpack 上（回测按文件比对、日志包按文件打包），先入库会把确定性产物路径与库路径搅成两套；
   `progress.jsonl` 等追加日志永远留文件（append-only 不要事务，SSE 按字节偏移 tail）。
   `out/_forecast_choices/` 与 job 私有快照里的 `forecast_choice.json` **不入库**：那是出稿时
   冻结的输入证据，必须不可变（见「范围外」）。
2. **库**：`out/_state/wenheng.sqlite`（`src/state_store.py`，stdlib `sqlite3`），
   `WENHENG_STATE_DB` 可覆盖（流水线子进程与 e2e 靠它）。函数一律注入 `db_path`。
3. **接口不动**：`approval.read/status/sign/revoke/fingerprint`、`workbench.load_review/toggle_flag/load_fills/save_fill`、
   `jobs.read_job/write_job/list_jobs/active_job/recover_stale/create_job`
   的签名与返回形状一个不改，只换内部实现（前端与 200+ 条 e2e 断言建在这些形状上）。
4. **签单不存 status**：库里没有 status / stale 列——签单是否失效，永远现场 glob + hash
   `out/<期次>/` 的 `red_slots.json` / `报告初稿_*.docx` / `table2.csv` 再比对（ADR 决定 6）。
   **任务记录相反**：`jobs.status` 就是事实本身（跑到哪一步），没有第二个真相源跟它比对，
   所以它既是 `payload` 的字段、又提升成列，供 `active_job()` 一次查询。
5. **`审批记录.md` 是导出件**：签/撤时仍写（内容从库记录渲染），因为 `jobs`/`archive`/e2e 当它是产物；
   它不再是真相。`approval.json` / `review.json` 降为导出件，由 `tools/state_export.py` 生成。
   任务记录的导出件是**日志包里的 `job/job.json`**：由库记录渲染（`archive._render_job`），
   磁盘上那份 `job.json` 既不写也不读。
6. **不自动导入**：库里没有而 `out/<期次>/approval.json` 存在时不隐式迁移（隐式行为难调试），
   由 `tools/state_import.py` 显式做：幂等、不删原文件、逐项打印导入 / 跳过 / 形状非法。
   `out/_jobs/*/job.json` 同样走这个工具（`import_jobs`），**一次性**；不读不代表删，原文件留着。
7. **迁移**：`migrations` 表 + 手写有序迁移；**库版本高于代码 → 只读降级 + 告警文案**，
   不抛、不拒启动（拒启动会让回滚也不可能）。
8. **并发**：`WAL` + `busy_timeout=5000`，每个写操作一个短事务，**不加跨进程锁**
   （沿用 uvicorn 单 worker + 单任务）；要多个写者就是迁 pgsql 的信号。

## 表结构

```sql
meta(key PRIMARY KEY, value)                       -- schema_version 等
migrations(id PRIMARY KEY, applied_at, note)
approvals(period PRIMARY KEY, actor, signed_at, payload)      -- payload=原文 JSON；无 status 列
approval_history(id INTEGER PK AUTOINCREMENT, period, ts, action, actor, payload)
reviews(period, key, value, payload, updated_at, PRIMARY KEY(period, key))
jobs(id PRIMARY KEY, status, period, created_at, updated_at, payload)  -- 迁移 002
manual_inputs(period, slot, value, status, actor, at, payload,
              PRIMARY KEY(period, slot))                            -- 迁移 003
sources(kind, scope, rel_path, size, mtime_ns, sha256, scanned_at, payload,
        PRIMARY KEY(kind, scope, rel_path))                         -- 迁移 004
```

- 期次键＝`out/<期次>/` 的**目录名**（`read(out_dir)` 只拿得到它）；`payload.period` 另行原样保留。
- `review` 现状是 `{位置: {state, by, at}}`，故一行一处：`key`＝位置、`value`＝`state`、
  `payload`＝`{by, at}`；`load_review` 读回同形（空库给 `{}`）。
- `jobs.payload` ＝原 `job.json` 的**完整字典**（含 `input`/`progress`/`console` 路径、`stats`、`exit_code`
  ……往返相等有单测）；`status / period / created_at` 是为查询提升的列，`updated_at` 是最后一次落库
  时刻（不混进 payload）。`out/_jobs/<id>/` 目录照旧创建——`progress.jsonl` / `console.log` /
  `forecast_choice.json` 还在里面，SSE 的字节偏移 tail 一点没动。
  **路径存仓库相对写法（2026-10-22 第二票）**：`input/云大全学科排名…xlsx`、
  `out/_jobs/<id>/progress.jsonl`（换算本体 `src/display_path.py`；口径与
  `out/_acquisition/*.json` 同一套）。仓库外的**兄弟目录**（母本来源
  `../数据与复现/…xlsx`）仍按仓库根写、只爬一层 `..`；再远（别的盘、`/tmp` 临时目录）
  才退回绝对路径——`../../..` 链子换台机器指到别处，写出来是编的。读口 `_prepare()`
  先按仓库根拼回绝对路径
  （档案页 / SSE / 日志包 / 重跑都当真实路径用），再对 `progress` / `console` 做
  「本职目录下同名文件」的重定位——历史记录与换了用户名的部署包仍能指回真文件。
- `manual_inputs` 现状是 `{位置::标记: {value, by, at}}`，故**一行一处**：`slot`＝那个键、
  `payload`＝该项原样字典（往返相等、导出逐字节可比）、`value / actor / at` 是提升列
  （`actor` 即旧文件的 `by`）。**`status` 不是真相**：三态（`pending/applied/orphan`）由
  `workbench._fill_state` 每次现场看 `red_slots.json` / 生成稿重算（同决定 4 的理由），
  库里只记落库那一刻的态，`get_fills` 不返回它。行序＝写入序（rowid），
  `state_export` 靠它保证 `manual_inputs.json` 与迁移前逐字节相同。
- `sources` 只装**清单与指纹**（`kind` ∈ `esi`/`incites`，`scope`＝期次或快照目录名，`rel_path`
  相对 `../数据与复现/`；`sha256` 空串＝只有元数据），**原始文件不入库、不改动**；`check` 是纯读、
  不建库。细节（增量指纹、`_root` 散件、与 `inventory.py` 的分工）见 sources 那份 spec。
- 建库走同目录唯一 tmp + `os.replace`（复用 `atomic_io.tmp_path`），不留半截表。
- 方言：`WAL` / upsert / `AUTOINCREMENT` 都是 sqlite 专有；**迁 pgsql＝重写本层 SQL**，不假装中立。

## 边界（写死）

1. **期次产物缓做**：`run_log.json` / `audit_record.json` / `env_snapshot.json` 不进库
   （理由见决定 1：它们挂在确定性产物与 logpack 上）；
   `out/_acquisition/`、`flexible/`、`progress.jsonl`/`console.log` 一律不碰。
2. **原始包不入**：ESI / InCites 原始包（9 GB 级证据）永不进库（ADR 决定 2）。
3. **签单不存 status**：见决定 4。
4. **任务记录不随包伪造**：部署包里带不带任务行，取决于打包时 `out/_state` 里有没有
   （打包脚本不造行、不删行）。真没有时界面**显式**说「这一期没有任务记录」
   （`web/src/lib/archiveStory.ts` 的 note / `Archive.tsx` 的 `progress_missing` 分支），
   不是空白页；`/api/status` 的 `active/last` 为 `null` 也是既有契约。

## 页面告警：只读降级（2026-10-22 落地）

`GET /api/status` 在既有 `{active, last}` 之外**新增一个字段**，既有字段一个不动（前端、e2e、
`web/src/api.ts` 都建在原形状上）：

```json
"state_db": {"ok": true, "schema_version": 3, "code_schema_version": 3,
             "degraded": false, "message": ""}
```

- `ok` / `degraded`：本机状态库现在能不能写。**库不存在＝`ok=true, degraded=false`**（还没签过单，
  不是病）；这个字段也**绝不顺手建库**——`state_store.health()` 只连已存在的文件（读口不造库）。
- `schema_version` / `code_schema_version`：库与程序各自的版本号，给日志与排查看，页面不用。
- `message`：降级时给馆员的**一句话**（如「本机数据存储版本比程序新，已进入只读模式，请联系管理员。」），
  正常时为空串；库里真正的技术说明只进服务端日志，不下发。
- 页面：`web/src/lib/stateDb.ts` 是纯函数（**只认后端明确说的 `degraded: true`**；字段缺失或形状非法
  一律按正常处理，不猜、不误警），`App.tsx` 登录后读一次，降级时在页首挂**常驻横幅**（复用既有
  `.banner.warn`）：哪些不受影响 / 哪些动作会失败（签单、撤回签单、标记存疑、在线填写后重出）/
  已签已填的记录不会丢。两种角色都看得到——这是环境故障，不是权限问题。
- **写入失败那一刻的话**（2026-10-22 同票第二步）：签单 / 撤回 / 标记存疑 / 在线填写真的写不进去时，
  接口回 `{error: "保存失败：本机数据存储版本比程序新，已进入只读模式，请联系管理员升级程序。
  这次操作没有生效，你的改动没有被保存。"}`——文案在 `src/state_store.py` 的
  `READONLY_NOTE` / `WRITE_FAILED_NOTE`，由 `write_error_note()` 统一翻译；**必须说清「这次没生效」**，
  且不出现库名 / 版本号 / 迁移 / `tools/state_export.py` 这类字眼（看到导出工具会被引去乱执行）。
  技术原文照旧完整进服务端日志（logger `wenheng.state`），日志才是排障入口。

## 打包脱敏（2026-10-22 落地）

「外发演示包 = 外发人名」：包里 `out/_state` 的 `actor` 列、`payload` 里的操作人、
`out/` 与 `input/` 下数据文件里的 `actor` / `by` / `operator`、`审批记录.md` 正文都带真实操作人。
`tools/make_deploy_pkg.py` 落包前做这些事，**真库一个字节都不碰**：

- **副本**：sqlite `backup` API 把主库复制到临时目录（不复制活库文件：WAL 未 checkpoint 时
  单拿主文件是半截快照），**名单也从副本上取**（`SELECT DISTINCT actor` 扫
  `approvals` / `approval_history` / `manual_inputs`，加 `jobs.payload.actor`、`reviews.payload.by`）。
  主库只经历打包前原有的 `wal_checkpoint(TRUNCATE)` 与一次只读打开；读 WAL 库时顺手产生的
  `-shm` 收尾即清（原有副文件与非空 `-wal` 一概不动）。
- **化名规则**：`admin` → `管理员`，其余 → `馆员`（**不清空**——演示要能看出「有人签过」）。
  副本的**所有文本列**逐格替换（提升列与 `payload` 一次到位），再 `VACUUM`，旧页里的原文不留。
  **批注等自由文本里的人名不在 actor 里**（真实数据就有：202609 一条历史批注写了人名），
  用 `--redact-term 词=化名` 追加，化名默认「馆员」；追加词与 actor 一起替换、一起被扫。
- **导出件重渲染**：包内每份 `out/<期次>/审批记录.md` 用脱敏后的库调
  `server/approval.py::_write_record` 重渲染（与签单时同一个渲染函数），替换包内原件；
  打包阶段会先把指纹覆盖的三件产物拷进临时目录，`status()` 判定与真目录一致。
- **数据文本**：`out/`、`input/` 下的 `.md` / `.json` / `.jsonl` / `.log` / `.csv` 等文本同样替换
  （实测 `out/202607/ai_calls.jsonl`、`out/_jobs/*/job.json`、`out/_acquisition/*.json` 都带 actor；
  未知扩展名**不替换**——漏掉就由下面的扫描兜住并让打包失败，不静默放过）。

**开关**：默认只要包里有 `out/_state` 就脱敏。`--no-redact` 显式关闭，**同时关闭泄漏扫描**
——这种包只能自用、不能外发，脚本会打醒目提示（并指出包里带真实操作人名）。

**验收判据（硬）**：打包完成后按**脱敏前**采集的真实名字扫一遍包——数据面（`out/`、`input/`）
逐个成员按字节扫、`.sqlite` 另按文本列逐格扫、非 ASCII 词（真实姓名，不是 `admin` / `demo`
这类角色标识）**全包扫**；命中即**删包、失败退出**并列出 member × 次数。
判据取「一个真名都不剩」而不是「改了几个字段」：改漏一个字段的包也是外发人名。
扫描覆盖不到 `.docx` / `.parquet` 的压缩内容——它们是产物，不是操作人记录。
代码与文档不在 ASCII 词的扫描范围：`admin` / `demo` 在代码里是角色标识与演示包名，不是人。

### 本机绝对路径与用户名（2026-10-22 第二票）

同一类外发信息还有本机路径：`C:\Users\<用户名>\Desktop\…` 既暴露开发机账号，换个用户名 /
换台机器也不成立。处理方式与 actor 一样「先换、再扫、漏了失败」：

- **换（只对副本）**：数据面文本与库内所有文本列把「本仓库根 + 分隔符」换成空
  （`C:\…\wenheng\out\x.json` → `out\x.json`）、把「本机家目录 + 分隔符」换成 `~/`。
  日志/正文只去前缀，分隔符原样保留；**库里的 `jobs.payload` 按 JSON 值整串归一成 posix**
  （`out/_jobs/<id>/progress.jsonl`），否则 Linux 部署机会把 `out\_jobs\…` 当成一个文件名。
  真库、真产物一个字节不动——老的绝对路径记录靠打包这一步变干净。
- **扫（两档范围，理由不同）**：①**通用形态**（盘符 `C:\` / `C:/`、`/home/`、`/Users/`）
  只扫**数据面 + 库内文本列**——代码与文档里合法地写这类前缀（docstring 举例、`.bat` 占位）；
  ②**本机实际路径**（本仓库根、`%USERPROFILE%` / `$HOME` 展开后的家目录）**全包扫**——
  任何成员里出现都是本机信息。定判据前跑过一遍现有仓库：通用形态若全包扫，
  `tools/*.py` 的 7 处硬编码开发机根目录会当场让打包失败（那批已改为从 `__file__` 推导）；
  两档分范围后现有 950 个成员的包 0 命中。正则判据**只扫正文扩展名**（`TEXT_SUFFIXES`）——
  `.docx` / `.png` / `.parquet` 按字节解出来的"文本"会随机撞上 `X:/`（实测报告初稿命中 98 次），
  那是噪声不是泄漏；本机路径这类字面判据按字节扫，二进制里也认得出来。

`stale` 语义不受影响：指纹只对 `out/<期次>/` 的 `red_slots.json` / `报告初稿_*.docx` /
`table2.csv` 取 sha256，与 actor 无关——打包后解包断言签单仍判 `signed`（用例
`test_脱敏不破坏签单有效性与指纹`）。

  **001 库升级到最新不丢签单**、**002 库升级到 003 不丢前两批数据**、**高版本只读降级**（不抛）；
  读口不造库（导入 `server.app` 时 `recover_stale()` 不会顺手建库，`get_fills` 也不会）；

  前端纯函数 `web/src/lib/stateDb.ts`：正常不告警、降级给后端那句人话、缺字段与形状非法按正常处理；

  不含盘符与用户名；仓库相对记录读出来拼回仓库下的绝对路径；`C:\Users\<用户名>\…` 的旧记录
  读出仍按同名文件重定位（文件不在则不假装存在）；

- 工具：导入幂等（重跑结果一致）、不删原文件、非法形状不落行；导出回原格式；
  **填写导出与迁移前文件逐字节相同**；**反向 e2e**：库 → `state_export` → 新库导入 → 逐字段相等
  （ADR 后果段要求的兜底；签单 / 存疑 / 填写各一条）；
- 回归：`pytest` / `ruff` / `e2e_check.py`（库级快照还原，不再备份 `approval.json` 字节；
  任务日志包断言改查「包里 `job.json` 的 id/status 是否与库里那条一致」）。

## 范围外 / 风险

- **`run_log.json` / `audit_record.json` / `env_snapshot.json` 不入库：它们是产物，不是状态。**
  三者挂在 `out/<期次>/` 的确定性产物与 logpack 上（回测按文件比对、日志包按文件打包），
  没有「谁在什么时候改的」这层语义；先入库会把确定性产物路径与库路径搅成两套。
- **`forecast_choice` 快照不入库：它必须不可变。** `out/_forecast_choices/<期次>.json`、
  job 私有快照、`_forecast_choice_applied.json` 是出稿时冻结的输入证据，用来回答
  「这份报告是哪套模型算的」；进了可变的状态库就不再是证据（同 ADR 决定 2 对原始包的理由）。
