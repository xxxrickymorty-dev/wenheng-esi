# spec：系统状态库（SQLite）——签单 / 复核 / 任务记录 / 人工填写入库（2026-10-21）

- **状态**：rick 已点头（ADR-0012，2026-10-21）→ ①（原子写）已在 `atomic_io` 收口；
  ②**签单与复核**已落地；③**任务记录**已落地；④**人工填写**（`manual_inputs`）已落地
  （2026-10-22，schema 003）；⑤期次产物缓做
- **票**：ADR-0012 决定 3 / 6 / 7 / 8 / 9 / 10 / 11；本 spec 是实施口径
- **红线前提**：状态库是**控制面**，不是数据面——数字仍只出自母本 xlsx，运行期 LLM 不进数据路径

## 决定

1. **范围**：已收 `approval`、`review`、**`job`**、**`manual_inputs`**。`run_log.json` /
   `audit_record.json` / `env_snapshot.json` **缓做**——它们挂在 `out/<期次>/` 的确定性产物与
   logpack 上（回测按文件比对、日志包按文件打包），先入库会把确定性产物路径与库路径搅成两套；
   `progress.jsonl` 等追加日志永远留文件（append-only 不要事务，SSE 按字节偏移 tail）。
   `out/_forecast_choices/` 与 job 私有快照里的 `forecast_choice.json` **不入库**：那是出稿时
   冻结的输入证据，必须不可变（见「范围外」）。
2. **库**：`out/_state/wenheng.sqlite`（`src/state_store.py`，stdlib `sqlite3`），
   `WENHENG_STATE_DB` 可覆盖（流水线子进程与 e2e 靠它）。函数一律注入 `db_path`。
3. **接口不动**：`approval.read/status/sign/revoke/fingerprint`、`workbench.load_review/toggle_flag/load_fills/save_fill`、
   `jobs.read_job/write_job/list_jobs/active_job/recover_stale/create_job`
   的签名与返回形状一个不改，只换内部实现（前端与 200+ 条 e2e 断言建在这些形状上）。
4. **签单不存 status**：库里没有 status / stale 列——签单是否失效，永远现场 glob + hash
   `out/<期次>/` 的 `red_slots.json` / `报告初稿_*.docx` / `table2.csv` 再比对（ADR 决定 6）。
   **任务记录相反**：`jobs.status` 就是事实本身（跑到哪一步），没有第二个真相源跟它比对，
   所以它既是 `payload` 的字段、又提升成列，供 `active_job()` 一次查询。
5. **`审批记录.md` 是导出件**：签/撤时仍写（内容从库记录渲染），因为 `jobs`/`archive`/e2e 当它是产物；
   它不再是真相。`approval.json` / `review.json` 降为导出件，由 `tools/state_export.py` 生成。
   任务记录的导出件是**日志包里的 `job/job.json`**：由库记录渲染（`archive._render_job`），
   磁盘上那份 `job.json` 既不写也不读。
6. **不自动导入**：库里没有而 `out/<期次>/approval.json` 存在时不隐式迁移（隐式行为难调试），
   由 `tools/state_import.py` 显式做：幂等、不删原文件、逐项打印导入 / 跳过 / 形状非法。
   `out/_jobs/*/job.json` 同样走这个工具（`import_jobs`），**一次性**；不读不代表删，原文件留着。
7. **迁移**：`migrations` 表 + 手写有序迁移；**库版本高于代码 → 只读降级 + 告警文案**，
   不抛、不拒启动（拒启动会让回滚也不可能）。
8. **并发**：`WAL` + `busy_timeout=5000`，每个写操作一个短事务，**不加跨进程锁**
   （沿用 uvicorn 单 worker + 单任务）；要多个写者就是迁 pgsql 的信号。

## 表结构

```sql
meta(key PRIMARY KEY, value)                       -- schema_version 等
migrations(id PRIMARY KEY, applied_at, note)
approvals(period PRIMARY KEY, actor, signed_at, payload)      -- payload=原文 JSON；无 status 列
approval_history(id INTEGER PK AUTOINCREMENT, period, ts, action, actor, payload)
reviews(period, key, value, payload, updated_at, PRIMARY KEY(period, key))
jobs(id PRIMARY KEY, status, period, created_at, updated_at, payload)  -- 迁移 002
manual_inputs(period, slot, value, status, actor, at, payload,
              PRIMARY KEY(period, slot))                            -- 迁移 003
```

- 期次键＝`out/<期次>/` 的**目录名**（`read(out_dir)` 只拿得到它）；`payload.period` 另行原样保留。
- `review` 现状是 `{位置: {state, by, at}}`，故一行一处：`key`＝位置、`value`＝`state`、
  `payload`＝`{by, at}`；`load_review` 读回同形（空库给 `{}`）。
- `jobs.payload` ＝原 `job.json` 的**完整字典**（含 `progress`/`console` 绝对路径、`stats`、`exit_code`
  ……往返相等有单测）；`status / period / created_at` 是为查询提升的列，`updated_at` 是最后一次落库
  时刻（不混进 payload）。`out/_jobs/<id>/` 目录照旧创建——`progress.jsonl` / `console.log` /
  `forecast_choice.json` 还在里面，SSE 的字节偏移 tail 一点没动。
- `manual_inputs` 现状是 `{位置::标记: {value, by, at}}`，故**一行一处**：`slot`＝那个键、
  `payload`＝该项原样字典（往返相等、导出逐字节可比）、`value / actor / at` 是提升列
  （`actor` 即旧文件的 `by`）。**`status` 不是真相**：三态（`pending/applied/orphan`）由
  `workbench._fill_state` 每次现场看 `red_slots.json` / 生成稿重算（同决定 4 的理由），
  库里只记落库那一刻的态，`get_fills` 不返回它。行序＝写入序（rowid），
  `state_export` 靠它保证 `manual_inputs.json` 与迁移前逐字节相同。
- 建库走同目录唯一 tmp + `os.replace`（复用 `atomic_io.tmp_path`），不留半截表。
- 方言：`WAL` / upsert / `AUTOINCREMENT` 都是 sqlite 专有；**迁 pgsql＝重写本层 SQL**，不假装中立。

## 边界（写死）

1. **期次产物缓做**：`run_log.json` / `audit_record.json` / `env_snapshot.json` 不进库
   （理由见决定 1：它们挂在确定性产物与 logpack 上）；
   `out/_acquisition/`、`flexible/`、`progress.jsonl`/`console.log` 一律不碰。
2. **原始包不入**：ESI / InCites 原始包（9 GB 级证据）永不进库（ADR 决定 2）。
3. **签单不存 status**：见决定 4。
4. **任务记录不随包伪造**：部署包里带不带任务行，取决于打包时 `out/_state` 里有没有
   （打包脚本不造行、不删行）。真没有时界面**显式**说「这一期没有任务记录」
   （`web/src/lib/archiveStory.ts` 的 note / `Archive.tsx` 的 `progress_missing` 分支），
   不是空白页；`/api/status` 的 `active/last` 为 `null` 也是既有契约。

## 验证

- 单测：路径口径（env 覆盖 / 期次同级 `_state`）、建库与 `schema_version`、签单与历史往返、
  复核增删、**任务记录往返相等 / 覆盖写不新增行 / 按期次与状态过滤**、
  **填写往返形状（不带 status）/ 覆盖写不新增行 / 按期次隔离 / status 只收三态**、
  **三态由产物现场判（库里 status 写什么都不改变判定）**、
  **`recover_stale` 在库上把 `running` 结为终态**、迁移幂等、
  **001 库升级到最新不丢签单**、**002 库升级到 003 不丢前两批数据**、**高版本只读降级**（不抛）；
  读口不造库（导入 `server.app` 时 `recover_stale()` 不会顺手建库，`get_fills` 也不会）；
- 工具：导入幂等（重跑结果一致）、不删原文件、非法形状不落行；导出回原格式；
  **填写导出与迁移前文件逐字节相同**；**反向 e2e**：库 → `state_export` → 新库导入 → 逐字段相等
  （ADR 后果段要求的兜底；签单 / 存疑 / 填写各一条）；
- 回归：`pytest` / `ruff` / `e2e_check.py`（库级快照还原，不再备份 `approval.json` 字节；
  任务日志包断言改查「包里 `job.json` 的 id/status 是否与库里那条一致」）。

## 范围外 / 风险

- **`run_log.json` / `audit_record.json` / `env_snapshot.json` 不入库：它们是产物，不是状态。**
  三者挂在 `out/<期次>/` 的确定性产物与 logpack 上（回测按文件比对、日志包按文件打包），
  没有「谁在什么时候改的」这层语义；先入库会把确定性产物路径与库路径搅成两套。
- **`forecast_choice` 快照不入库：它必须不可变。** `out/_forecast_choices/<期次>.json`、
  job 私有快照、`_forecast_choice_applied.json` 是出稿时冻结的输入证据，用来回答
  「这份报告是哪套模型算的」；进了可变的状态库就不再是证据（同 ADR 决定 2 对原始包的理由）。
- 部署包会带上审批记录＝馆员姓名，与「含姓名的文档不外发」口径冲突：**演示包审计另行脱敏**，本次不实现；
- 降级告警目前只在 `state_store.health()` + 服务端日志，页面横幅另票（不扩 `/api/*` 形状）；
- 回滚＝代码 + 库 + 包三样一起回（`state_export` 是唯一兜底）。**任务记录没有 `state_export`
  的反向导出**——回退旧代码前先用 `state_import` 跑过的原 `job.json` 仍在磁盘上，这就是它的退路；
- 换代码不换库时，旧代码（`SCHEMA_VERSION=1`）会把 002 的库判成「高于本程序」→ 只读降级。
  **升级=停服务→换代码→起服务**，别指望旧进程能继续签单。
