## 问题

灵活产线（第二条产线）的产出目前是一个**黑箱**：

1. **计划落了盘，但没人看得见**——`flex_plan.json` 静静躺在产物目录里，运行档案页没有它的位置；馆员和评审只能看到一份出好的稿。
2. **自检跑了，但没人管**——`self_check` 只把 `check_pass` 报出去，**不过也不重规划、不交人**；缺的两条锚点（计划↔执行比对、产出↔声明比对）根本没检。
3. 结果：对外讲「有 agent」，实际**自主不可见、把关不成环**——正是 31 号说的「自主面收得太紧 + 自主过程不可见」。

## 方案

1. **计划里写清校验点**：规划产出的计划加 `checks`——按意图由**规则**生成 3–5 条结构化校验点（模型**不**产生校验点，否则它会专挑容易过的）。
2. **自检补锚点、成环**：在既有 `self_check` 上补齐两条锚点；不过 → **重规划一次**（把失败原因当提示喂回）→ 仍不过 → **交人**（不硬出稿）。
3. **看得见**：运行档案页加一张「本期规划与校验」卡（计划摘要 / 校验判定 / 回退与交人记录），数据走既有档案口。

## 用户故事

2. 作为馆员，我想看到校验判定（通过/不过+原因），以便知道哪些数字是核过的。

11. 作为维护者，我想让 `checks` 落进**既有** `flex_plan.json`，以便不产生第二个计划文件。
12. 作为维护者，我想让成环复用 `heal` 的「给一次机会」语义（上限 1 次），以便全仓只有一种重试观。

## 实现决策

- **计划**：`checks` **不进** `_PLAN_KEYS`（模型不得提供——否则它会专挑容易过的校验点），由**规则在校验后注入**，随计划一起落**既有** `flex_plan.json`（不新建 `report_plan.json`——一事一文件；仍是**一套**计划语言）。计划**默认执行、事后可审**，不引入新的确认门。
- **`checks` 形态**（类型形状，编码的是决策不是实现）：

  ```
  checks: [ { kind, target, expect } ]
  kind   ∈ { "source_trace", "spec_query_match", "outline_match" }
  target ∈ { "all_points", "charts", "sections" }
  expect ∈ { "bidirectional", "declared==executed", "declared==emitted" }
  ```

  由**规则**按 `intent` 从固定模板生成 3–5 条；模型输出里出现 `checks` 一律剥离（同 `_validate_plan` 既有做法）。
- **校验（Critic）**：扩既有 `self_check`（`flexible/report.py`）——
  ① 保留四条既有项；
  ② 补 **来源链双向**：`spec` 的每个数据点必须在 `flex_sources.json` 有对应条目，**且**每条来源必须在 `spec` 有对应点（现只查单向）；
  ③ 补 **`spec` ↔ `queries` 执行记录比对**；
  ④ 补 **章节/图表清单比对**（计划声明 vs 实际产出）。
  判定**全部机械可核**；`pass` 仍是一个布尔，明细进 `flex_meta.json`。
- **成环**：不过 → **重跑 planner 一次**（失败原因作为提示喂回）→ 重跑构建；仍不过 → 结果标 `escalated`（交人），报告里明写。上限常量与 `heal` 同构（`MAX_HEAL_ATTEMPTS = 1` → 本处 `MAX_CRITIC_ROUNDS = 1`）。
- **归因解释（可选）**：失败原因的人话解释可经 `src/ai` 的 `diagnose` 能力生成；**判定不经模型**。模型出口仍唯一在 `src/ai/_attempt.py`。
- **可见面**：
  - 数据：**扩既有** `GET /api/periods/{p}/archive`，带出「本期规划 + 校验判定 + 回退/交人记录」；
  - 页面：运行档案页加一张「本期规划与校验」卡（三行：计划摘要 / 校验判定 / 回退与交人）；**无产物时不渲染**；
  - 生成台加一行「本期规划：…（点看）」入口。
- **界面词**：一律走 `GLOSSARY.md` 馆员话术（本期规划 / 数据校验 / 自动修复 / 需人工接手）；内部词（规划 Agent、校验 Agent、L0–L5）界面禁用。
- **度量（最小三指标）**：计划合法率 / 校验拦截率 / 单份时长——写进运行档案；**不上大屏**。
- **红线（不动）**：ADR-0005 三条——运行期 LLM 不进数据路径；台账只读；固定产线主干硬编码。本 spec 只动 `src/flexible/`、`server/` 的既有口、`web/` 的运行档案与生成台。

## 测试决策

- **好测试的标准**：只测**外部行为**——计划文件里有没有 `checks`、校验会不会红、接口吐不吐得出计划、卡片渲不渲染；不测内部函数怎么写的。
- **缝（优先级从高到低，共三条，不新增）**：
  1. **S1 `src/flexible/report.py::generate()`**（既有编排入口）——计划含 `checks`；坏例必红；重规划一次；仍不过标交人。先例：`tests/test_flexible.py`。
  2. **S2 `GET /api/periods/{p}/archive`**（既有档案口）——带出计划与判定；无产物时不带。先例：`tests/test_api_flexible.py`、`tests/test_server_artifacts.py`。
  3. **S3 `web/src/lib/`（vitest，按需）**——仅当「校验结果 → 界面文案」出现纯逻辑时。先例：`web/src/lib/status.test.ts`。
- **红队用例（验收判据②的载体）**：构造一份来源链缺一条目的产物 → `self_check` 必须 `pass=false`，且失败项指向 `source_trace`。
- **验收判据（三条，来自 Round2-Q7）**：①计划落盘且**人可读**（打开 `flex_plan.json` 看得懂）；②**注入坏例必拦**（红队用例）；③运行档案里**看得到**（截图或走一遍）。
- 回归：按根 `AGENTS.md` 交付清单跑（pytest 全量 / e2e_check / verify_demo_run / ruff）；UI 改动按 `web/AGENTS.md` 先静态稿。
