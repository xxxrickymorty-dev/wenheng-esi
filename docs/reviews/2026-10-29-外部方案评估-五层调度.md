## 三、三处硬冲突（照做会做坏）

### 冲突 1：正文交给 LLM 分章生成

它把「生成层」设计成章节 Agent 产出带引用标记的散文。

**在文衡不成立**，因为成品要盖章，而盖章要求三件事：

- **逐格可核**：704 个槽位逐一对得上台账；散文没有"格"，只有句子。
- **逐字节可复现**：同一期重出必须得到同一份文件。LLM 生成做不到（同一个 prompt 两次不同）。
- **跨期可比**：本期与上期并排读，结构必须一致；LLM 每期措辞漂移，读者无法比较。

它提的「论断—证据—来源」三元关联是**文档级引用**，防的是幻觉；
文衡要的是**格子级指针**（数字 → 台账某表某行某列），防的是错数。**防错数更硬。**

**折中**：LLM 写正文可以放在**灵活线**（内部参考稿，`src/flexible/`），不进复刻线。
文衡已经有这条线，且它的 `provenance.py` 做的就是来源链。

### 冲突 2：LangGraph 当调度骨架

**在文衡不成立**（当前阶段）：图是代码。N 份报告 = N 张手写图，扩展性问题原样保留，
只是从 Python 挪进了构图 DSL。而且 `STEPS` 是红线里的「唯一事实源」，
换成图等于删掉这条红线。

**它的正确位置**：执行层的一个实现。等声明层有了（`reports/*.spec`），
图由声明生成 —— 那时换 LangGraph 的验收判据是「spec 一字不改」。

### 冲突 3：多 Agent 角色分工（采集 / 分析 / 写作）

ADR-0005 第 3 条：**固定产线不上多 agent**。
多 agent 的收益在探索性任务（路径不预设），报告是固定流程（路径必须预设）。
代价是路径不确定、成本不可控、复现无门。

## 四、它漏掉的七个坑（都是文衡踩过的）

1. **数据不是 API，是导出包。** 字段不稳定：省域表列序 7／9／15 列三个版本，按下标读把 290 填成 41979。
2. **期次解析是单点。** 第 N 期 = 2N−1 月；期次猜错整期返工。目录名不是 6 位数字时，
   解析会退回"台账最新" —— 昨天重出 202605 时就踩了，产出了 202609 的稿。
3. **学科名对齐会静默失效。**「植物学与动物学」vs「植物与动物学」漏填 11 格，还报「231/231 全对」。
4. **同名归一。** 机构名脏写法、学院映射、作者名变体——都要显式别名表，不能模糊匹配。
5. **Word 母版工程比生成难十倍。** 合并单元格、母版残留文本、原生图表与位图的边界、
   槽位几何。这些在"生成一份 docx"的方案里不会出现。
6. **对照差异报告要能归因。** 昨天的实例：202607 对照件标了「❌ 多学科排名」，
   结论段却只写「行级通过 21/22」——**发现了，但被平均数吞掉**。这类问题它完全没覆盖。
7. **盖章这件事本身。** 章是谁的、责任是谁的、数据授权在谁手里——它一句没提。

## 五、可以摘的三件（不改架构）

1. **取数预算**：给取数核验加「本期配额与缓存记录」（现在是登记制，没有预算制）。
2. **证据索引导出**：现有 `red_slots.json` 的 `source` 是文件名，不是格子指针。
   可加一份机器可读索引：`数字 → 表/行/列/期次/脚本版本`。这是评审加分项。
3. **评测基线**：它说"质量侧基线要自己建"。文衡该建的是一条
   「AI 初稿 + 馆员复核」与「纯人工」的时间/返工率对比——现在只有效率侧（分钟级），没有质量侧。
