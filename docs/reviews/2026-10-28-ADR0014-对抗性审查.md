## S0-1 现在的代码就有一处静默错位（不是未来风险）

**指控**：`src/fill_docx.py::fill_big_table` 按 CSV 行序写 `big.rows[i]`，**不校验**第 0 列学科名与
`DISCIPLINES_CN[val]` 是否一致；也不校验 `t2` 行数是否为 22。

**证据**：

```python
for i, (_, row) in enumerate(t2.iterrows(), start=1):     # 行序即契约，但无断言
    ...
    old = big.rows[i].cells[j].text.strip()
    if old != text:
        set_cell(big.rows[i].cells[j], text)               # 直接写，不问这一行是谁
```

`src/compute.py:90` 已有 `sort_values("_prox_change", ascending=False)`——本项目存在**按数值排序**的表。
一旦 T01 源行序变（换期次、改口径、某人调了排序），22 个学科的数字整体错位。

**如果为真**：报告照常生成、照常盖章。11 列 × 22 行全错，而每个数字都"像真的"。
`old != text` 仍会触发，红件清单也照常记录——**记录的是错位后的值**。人工核对极难发现。

**修法（一行，加在 `set_cell` 之前）**：

```python
assert norm_disc_cn(big.rows[i].cells[0].text.strip()) == DISCIPLINES_CN[val], \
    f"T01 行序与 table2 不一致：r{i} 是 {big.rows[i].cells[0].text}，应为 {DISCIPLINES_CN[val]}"
```

**这条比 ADR-0014 里任何架构讨论都值钱。** 它不需要新架构，只需要一次断言。

## S0-2 那个「77%」是构造的，不是实测

**指控**：`0.95⁵ = 77%` 假设每步 3 个候选、每步独立 95% 正确。
真实候选是 13 个工具，模型还能读上文纠错。这个数字**没有实测来源**。

**我在 2026-10-28 用了它三次**：对话里、两页 HTML 里、ADR-0014「为什么」段里。

**如果被追问**：「你们测过吗？」——答不出。整段论证贬值，并连累真正成立的那部分（不可复现）。
评审对"编出来的精确数字"极敏感，一旦抓到，前面所有数字都会被怀疑。

**修法**：删掉百分比，只留机制——

> 路径数随步数指数增长；模型调用不保证同输入同路径，因此「逐字节一致」无法成立。

要保留数字，就必须真的跑一次统计：同一问题 N 次，记录工具序列有多少种。

## S1-1 声明层可能是 ADR-0013 的重犯

**指控**：0013 刚删掉「同数据两套壳」（台账镜像），理由是**不为一个消费者养一层壳**。
声明层今天的消费者**只有一个**（一份双月报告）。

**区别必须被证明，不能被声称**：第二、第三消费者（推广、加报告、灵活定制）若在近期不出现，
声明层就是同一类死代码，只是更大。

**修法**：先做有两件**立即消费者**的事——工具账本、校名外置（58 处 / 19 文件）。
声明层的 schema 设计延后到第二个报告真的立项时。

## S1-2 `w:sdt` 在 WPS 下未验证

**指控**：L2 方案的核心是 Word 内容控件打 tag。但——

- `python-docx` 无 SDT 原生 API，需走 lxml；
- **WPS 对 `w:sdt` 的保留行为未验证**。国内高校图书馆大量使用 WPS。

**如果为真**：WPS 保存一次后 tag 丢失或被重组，整套 L2 方案作废。

**修法（30 分钟，在写任何代码之前）**：造一个含 3 个 SDT 的 docx → 用 WPS 打开 → 另存 →
解包 `word/document.xml` → 看 `w:tag` 是否还在。这一步不过，L2 全部重想。
