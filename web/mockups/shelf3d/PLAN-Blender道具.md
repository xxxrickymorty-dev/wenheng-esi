## 2. 选定做法

### 2.1 分工：几何归 Blender，材质归代码

| 谁 | 干什么 |
|---|---|
| Blender（headless 脚本） | **只出几何**：顶点 / 法线 / UV / 索引 + 部件名 |
| Three.js | 出**材质**：沿用现有配方（木 `roughness .62` / 金属 `metalness .90` / 布 `sheen .30`…） |

**为什么只出几何**：Blender 的 Principled BSDF 不能 1:1 映射到 three 的物理材质；
我们现有材质是**程序化 canvas 贴图 + 手调参数**（从参考站拆解 + 实测调出来的），
搬 Blender 材质 = 把已经调好的东西丢掉重来。各干最擅长的。

### 2.2 导出格式（先冻结，避免后面反复改）

```js
window.WH_MESHES['reading-desk'] = {
  bbox: [w, h, d],                 // 便于摆位与自检
  parts: [
    { name: 'top',   mat: 'wood',
      pos: '<base64 Float32>', nrm: '<base64 Float32>', uv: '<base64 Float32>',
      idx: '<base64 Uint16>' },
    { name: 'leg-1', mat: 'metal', /* … */ }
  ]
};
```

- **base64 编码二进制**，不用数组字面量：字面量体积是二进制的 3–4 倍，解析还慢
- 运行时解码 3 行：`Uint8Array.from(atob(s), c => c.charCodeAt(0)).buffer` → `new Float32Array(buf)`
- `mat` 是**材质槽名**（`wood` / `metal` / `fabric` / `paper` / `glass`），映射到已有材质工厂

### 2.3 建模约定（脚本必须遵守，否则一定出问题）

| 项 | 约定 | 为什么 |
|---|---|---|
| 坐标系 | Blender Z-up → 导出时**转 Y-up**（绕 X 转 −90°） | three 是 Y-up；不转就是躺着的 |
| 原点 | 每个道具的原点放**底面中心** | 摆位时 `position.y = 地面高度` 一句话搞定 |
| 单位 | 1 Blender 单位 = 1 米 | 我们的书是 0.44 × 0.68 |
| 朝向 | 正面朝 **−Y**（导出后朝 +Z） | 与现有物体一致 |
| 变换 | 导出前**全部 apply**（location/rotation/scale 归零） | 否则法线被错缩放 |
| 三角化 | 导出前三角化（`bmesh.ops.triangulate`） | 避免 NGON 在 three 里的兼容问题 |
| 法线 | 保留硬边/平滑分组（custom split normals） | 否则木桌的棱会糊成一团 |
| 命名 | 部件名用 ASCII（`top` / `leg-1` / `shade`） | 中文名在导出与调试里都麻烦 |
| 面数 | 单件 ≤ 5000 三角面 | 背景道具不该吃性能 |

### 2.4 三条铁律

1. **脚本与输出走 ASCII 路径**（如 `F:\blender\wenheng\`），最后再拷回仓库——
   Blender 在 Windows 下对非 ASCII 路径不稳（本项目在 PowerShell 上已吃过同款亏）
2. **几何与材质解耦**（见 2.1）
3. **每件道具先出"最小样件"再批量**（先一个方块打通链路）

## 3. 被否掉的选项

| 选项 | 否掉理由 |
|---|---|
| **A · `.glb` + GLTFLoader** | 多 ~50KB 依赖；`.glb` 是外部文件，`file://` 下 `fetch` 被 CORS 拦 → 只能内联 base64（再涨 33%）；而 GLTFLoader 的真正价值（材质/动画/骨骼/蒙皮）我们一样用不上 |
| **C · 烘成贴片** | 远景够用，但**近处会露馅**：不能绕、不能点亮、没有厚度。阅览桌/台灯是**前景道具** |
| 直接导出 Blender 材质 | 映射失真 + 丢掉已调好的配方（见 2.1） |
| 顶点量化 + octahedral 法线编码 | 体积能再降 ~60%，但现在不缺这点体积（一个道具 2–5KB）→ 违反 YAGNI，**留作后手** |

## 4. 风险与「什么信号出现时该改主意」

| 风险 | 信号 | 改什么 |
|---|---|---|
| Blender 5.2 的 Python API 与网上 4.x 教程不同 | 脚本报 `AttributeError` | 只用 `bpy.data` / `bmesh` 层 API（这两层最稳），少碰 `bpy.ops` |
| headless 下缺 UI 上下文 | `RuntimeError: context is incorrect` | 同上：不用依赖视图的操作；必要时 `bpy.context.view_layer.update()` |
| 导出体积超预期 | 单件 > 20KB | 上顶点量化（后手） |
| 加入后帧率掉 | 三角面总数 > 5 万 | 减面；远景道具改贴片（方案 C） |
| 道具与书架风格不搭 | rick 说"不像一套" | 回到"材质配方优先"：几何再准，材质不统一也会散 |

## 6. blender-mcp 要不要装

**建议：先不装。**

- 它提供的是**交互式控制**（实时问 Blender 场景、边看边调）——而我们的用法是**批处理**（脚本进、文件出），这份交互能力用不上
- 代价：一个常驻进程 + 一份 MCP 配置 + **安全面**（MCP 能跑 Blender 的任意 Python）
- **什么时候再装**：如果第 ③④ 步变成"反复调参数、需要看着 Blender 现场改"，那时装才有意义
- 若仍要装：它是可选增强，**不影响本计划**；我会把它当"调试期工具"，产物仍走脚本导出
